# 埋点方案

这套埋点是**自建**的：事件在小程序端收集 → 批量上报到自己的后端 → 落盘 + 按天汇总 → 网页看板展示。
不依赖第三方统计平台，数据在自己手里；同时也预留了微信官方「自定义分析」的双写开关（`config.tracker.officialAnalytics`）。

---

## 一、你必须关心的三个指标

### 1. UV（独立访客）

| 项目 | 说明 |
| --- | --- |
| 上报事件 | `app_launch`（冷启动）+ `page_view`（页面曝光） |
| 去重键 | `uid` —— 匿名设备 ID |
| 计算位置 | 服务端，按天对 `uid` 去重（`rollup.uv` 是个集合） |
| 口径说明 | 同一台手机一天内多次打开只算 1 个 UV；清缓存 / 换手机会算成新的 UV |

`uid` 怎么来的：`miniprogram/utils/tracker.js` 里首次启动时生成 `u_xxx`，存在本地 `qy_track_uid`。
它**不包含任何个人身份信息**，只用来做去重。用户登录后，`uid` 会和 `openid` 一起上报，方便把设备和用户对上。

> 为什么不用 `openid` 当 UV？因为没登录的用户拿不到 `openid`，只按 `openid` 算会漏掉大量访客。

### 2. 计算次数（核心业务指标）

有两个口径，看板上同时展示，用来交叉验证：

| 口径 | 数据来源 | 说明 | 建议 |
| --- | --- | --- | --- |
| 服务端口径 | `server/data/rollup/<日期>.json` 的 `server.parse_success` | 后端真的解析成功才 +1，**客户端无法伪造** | 对外汇报用这个 |
| 客户端口径 | `parse_success` 埋点 | 能看到发起、失败、耗时、平台等细节 | 做漏斗和排障用 |

相关事件：`parse_submit`（点按钮）→ `parse_start`（发请求）→ `parse_success` / `parse_fail`（结果）。
看板上的「解析成功率」= `parse_success / parse_start`。

服务端还会额外记两条**权威事件**（写进 `events/<日期>.server.jsonl`，客户端无法伪造）：

| 服务端事件 | 含义 | 怎么看 |
| --- | --- | --- |
| `server.parse_success` / `server.parse_fail` | 后端真实解析成功 / 失败，带 `provider`、`cost_ms` | 对外报「计算次数」用这个；失败多了就是服务商或平台出问题了 |
| `server.credit_consumed` | 保存到相册时真实扣掉的次数 | 「保存」的权威口径，和客户端 `download_success` 对照看 |
| `server.reward_granted` | 看完广告成功发出去的次数 | 广告变现的转化数，比客户端 `ad_reward_success` 更可信 |
| `server.parse_blocked` | 解析撞上每日防刷上限被拦 | 正常应该是 0；持续有值说明有人在刷你的接口费 |

> 注意：**解析是免费的**，不扣次数；次数只在「保存到相册」时消耗。
> 所以「计算次数」和「保存次数」是两个不同口径的指标，看板上分开看。

### 3. 广告点击

**先记住一个前提：微信广告组件不提供点击回调。**

| 广告类型 | 微信给的仅有的回调 |
| --- | --- |
| Banner（`<ad>` 组件） | `bindload` / `binderror`，**没有 click** |
| 插屏广告 | `onShow` / `onClose`，**没有 click** |
| 激励视频 | `onLoad` / `onError` / `onClose(isEnded)`，**没有 click** |

所以「广告点击」在自建埋点里分成两类统计，看板上分开显示：

| 类型 | 事件属性 | 触发点 | 可信度 |
| --- | --- | --- | --- |
| 用户主动点击 | `ad_click` + `method=intent` | 用户点「保存到相册」后确认看广告（`ad.showRewardedVideo()`，`position=result_save`） | 准，推荐作为主指标 |
| 广告区域点击 | `ad_click` + `method=area_tap` | 用户点击 banner 广告位所在区域 | 估算值，原生组件可能不冒泡，只会偏少 |

> 想要**权威**的曝光 / 点击数据，看微信公众平台「流量主 → 数据」；
> 自建埋点的价值是：能和「解析 → 保存」这条业务漏斗串起来看，知道广告到底带来了多少留存和转化。

各类型广告的埋点覆盖情况：

| 广告类型 | 可埋到的点 |
| --- | --- |
| Banner | `ad_load`（加载成功，同时记 `ad_show`）、`ad_load_fail`、`ad_click(area_tap)` |
| 插屏 | `ad_show`、`ad_close`、`ad_load_fail`（没有用户点击，所以只有曝光） |
| 激励视频 | `ad_click(intent)` → `ad_show` → `ad_close(is_ended)` → `ad_reward_success` → `reward_claim_success` |

激励视频的完整链路都打点了：`ad_click(intent)` → `ad_show` → `ad_close(is_ended)` → `ad_reward_success` → `reward_claim_success`（服务端发奖成功）。
所以你能算：**看到广告的人里，有多少真的看完并领到了次数**。

## 二、上报机制（为什么这套埋点比较耐造）

```
业务代码 → tracker.track('事件名', {属性})
              │
              ├─ 内存队列（最多 300 条，超出丢最旧的）
              │     └─ 1 秒防抖写入本地 storage（防止闪退丢数据）
              │
              ├─ 触发上报的时机：
              │     ① 攒够 8 条
              │     ② 每 5 秒定时
              │     ③ 关键事件立刻发（app_launch / parse_success / parse_fail
              │        / ad_click / ad_reward_success / download_success）
              │     ④ 小程序切后台（app.onHide）
              │
              └─ POST /api/track  { app: 公共参数, events: [...] }
                        │
                        ├─ 成功：清掉已发送的，继续发剩下的
                        └─ 失败：指数退避重试（3s/6s/9s，最多 3 次），
                                 仍失败就留在本地，下次启动补发
```

几个关键设计：

- **每条事件带客户端时间戳 `ts`**：补发的事件会按它原本发生的时间归到正确的自然日，不会因为补发而算到第二天。
- **`seq` 自增序号**：出问题时可以判断有没有丢包。
- **`sid` 会话 ID**：30 分钟无操作算一个新会话，用来算人均使用次数和会话时长。
- **服务端按 token 里的 `openid` 覆盖客户端传的用户标识**，避免被伪造。

事件的数据结构：

```json
{
  "e": "parse_success",
  "uid": "u_lz8x2k9d1",
  "sid": "s_lz8x2k9e7",
  "ts": 1758550123456,
  "seq": 42,
  "p": "pages/index/index",
  "r": "pages/index/index",
  "props": { "platform": "douyin", "cost_ms": 1260 }
}
```

## 三、事件字典

> 加新事件：先在 `miniprogram/utils/tracker.js` 里 `track('事件名', {...})`，再到 `server/src/store.js` 的 `aggregate()` 里加一个 `case`（不加也能存进原始流水，只是不会出现在汇总里）。

### 生命周期

| 事件名 | 触发时机 | 关键属性 |
| --- | --- | --- |
| `app_launch` | 小程序冷启动 | `scene`、`scene_name`、`path`、`from_uid`、`from`、`cold_start` |
| `app_show` | 从后台切回前台 | `scene`、`path` |
| `app_hide` | 切到后台 | 无 |
| `page_view` | 页面 `onShow` | `path` |
| `page_leave` | 页面 `onHide` / `onUnload` | `path`、`stay_sec` |
| `login_success` | 静默登录成功 | `is_new_user`、`openid_tail`、`from_uid` |
| `login_fail` | 登录失败 | `msg` |
| `js_error` | 全局 JS 异常 | `msg`、`stack` |
| `unhandled_rejection` | 未处理的 Promise 异常 | `msg` |
| `api_error` | 接口报错 | `url`、`status`、`code`、`msg` |

### 去水印主流程

| 事件名 | 触发时机 | 关键属性 |
| --- | --- | --- |
| `paste_success` / `paste_fail` | 点击「粘贴链接」的结果 | `platform`、`has_content` |
| `input_clear` | 清空输入框 | 无 |
| `parse_submit` | 点击「一键去水印」 | `platform`、`has_url`、`input_len`、`credits` |
| `parse_start` | 真正发起解析请求 | `platform` |
| `parse_success` | 解析成功 | `platform`、`cost_ms`、`media_type`、`request_id` |
| `parse_fail` | 解析失败 | `platform`、`code`、`msg`、`cost_ms` |
| `result_view` | 进入结果页 | `request_id`、`platform`、`media_type` |
| `result_play` | 播放预览 | `request_id` |
| `download_start` | 点击保存到相册 | `request_id`、`media_type` |
| `download_success` | 保存成功 | `request_id`、`media_type` |
| `download_fail` | 保存失败 | `request_id`、`reason`（如 `auth_deny`） |
| `copy_link` / `copy_text` | 复制直链 / 复制文案 | `request_id` |
| `history_open` / `history_delete` / `history_clear_all` | 历史记录操作 | `id` |

### 广告

| 事件名 | 触发时机 | 关键属性 |
| --- | --- | --- |
| `ad_click` | **广告点击（核心）** | `ad_type`、`position`、`method`(intent/area_tap)、`ad_unit_id` |
| `ad_load` | 广告加载成功 | `ad_type`、`position` |
| `ad_load_fail` | 广告加载失败 | `ad_type`、`code`、`msg` |
| `ad_show` | 广告展示成功 | `ad_type`、`position` |
| `ad_show_fail` | 广告展示失败 | `ad_type`、`position`、`retry` |
| `ad_close` | 广告关闭 | `ad_type`、`is_ended`（激励视频是否看完） |
| `ad_reward_success` | 激励视频完整观看 | `ad_type`、`position`、`scene` |
| `ad_unavailable` | 广告位不可用（没开通/占位 ID） | `position` |
| `save_need_ad` | **点保存时次数不够，弹出了广告引导**（核心漏斗节点） | `position=result_save` |
| `credit_consume_success` | 保存前扣次数成功 | `request_id`、`left`（扣完还剩几次） |
| `credit_consume_fail` | 扣次数时服务端异常（网络抖动，已放行保存） | `code`、`msg` |
| `reward_claim_success` / `reward_claim_fail` | 服务端发奖结果 | `added`、`left`、`scene` |
| `reward_modal_cancel` / `reward_not_completed` | 用户放弃看广告 | `reason`（`skip`=中途退出，`failed`=没放出来，`unavailable`=广告位不可用） |
| `ad_fail_open` | 广告放不出来，这次放行让用户保存 | `position`、`reason` |

> `ad_fail_open` 是刻意设计的**兜底**：广告加载失败时不硬拦用户，这次直接给保存。
> 硬拦会造成「点了保存什么都没发生」——那是差评和投诉的头号来源。
> 想看这个兜底触发了多少次，看板搜 `ad_fail_open` 就行；如果量很大，说明广告位配置有问题。

> banner 广告没有独立的「展示」事件，**加载成功即视为已展示**，所以 `handleBannerLoad()` 会同时记一条 `ad_show`，
> 这样看板上的「广告展示」对三种广告才是统一口径。

### 分享

| 事件名 | 触发时机 | 关键属性 |
| --- | --- | --- |
| `share_click` | 点击分享（按钮 / 朋友圈） | `channel`、`page` |
| `app_launch` 带 `from_uid` | 别人通过分享卡片打开 | `from_uid`、`from=share` |

分享拉新怎么算：分享出去的路径带着分享者的 `uid`（`?from_uid=xxx&from=share`），
新用户打开时 `app_launch` 会带上它，服务端统计为 `new_user_from_share`（分享带来的新增设备数）。

### 公共参数（不占事件体积，每次上报带一次）

`app_id`、`app_version`、`env_version`、`sdk_version`（基础库）、`wx_version`、`platform`、`system`、`brand`、`model`、`window_width/height`、`pixel_ratio`、`user_id`、`first_visit`。

## 四、数据存哪儿

```
server/data/
├── events/
│   ├── 2026-09-22.jsonl          原始事件流水（一行一条 JSON，方便 grep / 导出 / 排查）
│   └── 2026-09-22.server.jsonl   服务端自己产生的权威事件（parse_success 等）
├── rollup/
│   └── 2026-09-22.json           当天汇总：UV 集合、各事件计数、分平台、分场景、分小时、广告明细
├── quota/
│   └── 2026-09-22.json           当天每个用户的次数消耗 { openid: { used, reward } }
├── users.json                    用户档案：首次/最近出现时间、累计解析次数
└── uv_index.json                 uid → 首次出现日期（用来算「新增用户」）
```

- 内存里维护当天汇总，**每 2 秒防抖落盘**，进程退出时也会保存一次。
- 数据量参考：每天 1 万条事件 ≈ 2MB 流水、几百 KB 汇总，单机随便跑。
- 要查某个具体问题：`findstr "u_xxxx" data\events\2026-09-22.jsonl`（Windows）或 `grep` （Linux/Mac）。

## 五、怎么验证埋点是对的

```bash
cd server
node index.js          # 一个终端启动服务
node tools/smoke-test.js   # 另一个终端跑冒烟测试
```

冒烟测试会模拟一次完整使用（启动 → 解析 → 看广告 → 保存 → 分享），然后检查三个核心指标能不能读到数据。

在微信开发者工具里调试时：
- `config/index.js` 里 `tracker.debug = true`（dev 环境默认开），控制台会打印 `[tracker] 事件名 {...}` 和每次上报结果。
- 想确认没丢数据：停掉服务端，随便点几下，再把服务端启动起来，看控制台有没有「补发上次未上报的事件 N 条」。

## 六、埋点常见坑（都踩过了）

1. **`wx.getClipboardData` 必须在用户点击事件里调用**，所以本方案是「点粘贴按钮」读取，而不是进首页自动读剪贴板。
2. **`wx.request` 在切后台后不一定能发完**，所以 `app.onHide` 时先把队列写进本地，下次启动补发。
3. **不要用 `openid` 当 UV**，未登录用户拿不到 `openid`，会严重低估。
4. **服务端要覆盖客户端传的用户标识**（以 token 为准），否则埋点接口就是一个可以被伪造数据的入口。
5. **事件属性只允许字符串/数字/布尔**，对象会被序列化后截断，超长字符串会被裁到 500 字符（防止有人塞垃圾把存储撑爆）。
